# ChainFlow Module Standard V0.1

## 为什么需要统一模块标准

ChainFlow 的每一个工具都是一个"能力模块"。它们可以由不同的人在
不同时间、使用不同编程语言和算法开发，但如果不遵守同一套"合同"，
以后这些工具就无法互相调用、无法组合成决策链、无法在同一个系统中
协同工作。

统一标准的作用不是限制创造性，而是保证：

- 单个工具可以独立交付给只需一个功能的小微企业；
- 多个工具可以组合给需要完整决策链的中型企业；
- 未来任何工具都能被 Agent 或决策中枢调用；
- 不同 AI 或开发者可以在同一套规则下协作。

## 核心原则：外层严格，核心对象逐步统一，内部 Payload 灵活

- **外层严格**：模块身份、请求格式、结果格式、错误格式、版本号、
  日志和人工确认节点，所有工具必须一致。
- **核心对象逐步统一**：企业、供应商、SKU、订单、库存、仓库、位置
  等公共对象，尽量使用统一名称和最小公共字段。
- **内部 Payload 灵活**：排线、选址、预测等不同工具的专属业务数据
  可以完全不同，放在各自的 `data`、`config`、`constraints` 和
  `result` 字段里。

## 每个模块必须满足

### 1. 独立可用

能单独解决一个明确的供应链问题。不需要依赖其他模块或系统就能
提供完整价值。

### 2. 独立交付

可以单独部署给只需要一个功能的小微企业、团队或个人用户。

### 3. 标准接入

遵守统一的：

- 请求格式（`common-request.schema.json`）
- 结果格式（`common-response.schema.json`）
- 错误格式（`common-error.schema.json`）
- 业务对象命名（`business-objects.md`）
- 版本规范
- 日志结构

### 4. 可被调用

可以被其他模块、Agent 或未来 ChainFlow 决策中枢调用。
调用方不需要了解模块内部实现。

### 5. 组合增值

多个模块组合以后，能形成更完整的供应链决策链。例如：

> DemandFlow 预测需求 → StockCheck 判断库存缺口 →
> SupplierScore 评估供应商 → NetworkFlow 比较仓网 →
> RouteFlow 生成履约方案

### 6. 持续沉淀

在合法授权和数据安全边界内，逐步积累：

- 业务模板
- 数据结构
- 规则
- 用户反馈
- 案例
- 决策结果

## 模块概念动作

每个工具在概念上必须支持：

| 动作 | 说明 | 适用层级 |
|------|------|----------|
| `validate(input)` | 检查输入数据是否合格，返回错误清单 | 所有 |
| `run(input)` | 执行工具核心逻辑 | 所有 |
| `explain(output)` | 把技术结果解释成业务人员能理解的文字 | 所有 |
| `health()` | 返回模块是否正常运行 | 所有 |
| `simulate(input)` | 模拟不同参数下的结果 | 决策层 |
| `compare(inputs)` | 比较多组输入下的方案优劣 | 决策层 |
| `feedback(decision_result)` | 记录人工选择与实际执行结果 | 决策层 |

这些是能力合同，不要求所有工具必须用同一种语言实现，
不要求现在立刻建设公网 API。

## 版本规范

- 使用语义化版本号：`主版本.次版本.修订号`（如 `0.1.0`）
- `module.json` 中必须写明当前版本
- 公共标准升级使用独立版本号（如 `0.1`、`0.2`、`1.0`）
- 结果中的 `module_version` 字段标明本次运行使用的版本

## 向后兼容原则

- 新增字段优先设为可选
- 已发布版本不得无故删除字段
- 需要废弃字段时，先标记为 `deprecated`，至少保留一个次版本周期
- 公共对象字段改名需要评估对所有模块的影响
- 标准升级需要在 `chainflow.md` 的关键决策记录中说明原因

## 何时使用模块专属扩展 vs 修改公共标准

**优先使用模块专属扩展**的情况：
- 只有一个模块需要这个字段
- 不确定其他模块是否需要
- 字段含义与模块业务逻辑强绑定

**考虑修改公共标准**的情况：
- 至少两个模块需要同一个概念
- 该概念可能被上层决策系统消费
- 该概念属于供应链通用对象

## 标准变更流程

1. 先在模块内使用扩展字段验证
2. 如果确实需要进入公共标准，提交变更提案
3. 评估对现有模块的影响
4. 尽量保持向后兼容
5. 更新 `business-objects.md` 和相关 Schema
6. 在 `chainflow.md` 关键决策记录中登记
7. 公共标准版本号升级

## 新工具开发流程

1. 完成 `docs/module-briefs/<module-name>.md` 立项说明
2. 从 `templates/module-template/` 复制模板
3. 填写 `module.json`、`input.schema.json`、`output.schema.json`
4. 实现 `validate`、`run`、`explain`、`health`
5. 编写 `README.md`
6. 添加示例和测试
7. 代码评审通过后合并
